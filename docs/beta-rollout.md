# عرضهٔ آزمایشی و تنظیم محافظ‌ها

این راهنما خروجی فاز چهارم است؛ تأیید آمادگی کامل برای عرضهٔ عمومی نیست. تست محلی، بار واقعی
MariaDB/cPanel، تأخیر ارائه‌دهندهٔ AI و محدودیت متغیر تلگرام را بازسازی نمی‌کند.

## قبل از استقرار
- از DB backup بگیرید و روش بازگردانی را خارج از بات آماده نگه دارید.
- بات و watchdog را متوقف و نسخهٔ جدید/وابستگی‌ها را نصب کنید. تنها یک polling process مجاز است.
- این فاز migration/env جدید ندارد؛ اگر فاز قبلی نصب نشده، تا `0012_outbound_cooldown` ارتقا لازم است:
```sh
$HOME/virtualenv/filo/3.11/bin/python3 -m alembic upgrade head
```
- تنظیمات `INPUT_RATE_*`، `AI_*` و `OUTBOUND_*` را مطابق .env.example بازبینی کنید؛ فعلاً defaults
  محافظه‌کارانه را نگه دارید. تغییرها restart لازم دارند؛ DB flood cooldown را برای دورزدن محدودیت پاک نکنید.
- سهمیهٔ رایگان روزانه و هزینه/صورتحساب ارائه‌دهندهٔ AI را بازبینی کنید. در صورت امکان hard spending cap
  بگذارید؛ هشدار هزینه به‌تنهایی جلوی خرج را نمی‌گیرد. محافظ نرخ جای سقف هزینه را نمی‌گیرد.
- مسیر حذف اطلاعات، توکن‌های محرمانه، دسترسی ادمین و backup را کنترل کنید. فایل env را commit نکنید.

## آزمون زندهٔ کوچک (بدون اسپم عمدی)
با تعداد کمی حساب آزمایشی خودتان، قبل از دعوت عمومی:
1. /start، عضویت/بررسی دوباره، راه‌اندازی شخصیت و اتصال بیزینسی را آزمایش کنید.
2. در حالت پیش‌نویس و خودکار، ارسال صحیح، مکث و takeover را بررسی کنید؛ UI رد نرخ را با خطای
   نامطمئن ارسال اشتباه نگیرید. در نامطمئن، پیش از هر اقدام تازه چت مقصد را بررسی کنید.
3. با چند پیام نزدیک و سپس با فاصلهٔ عادی، رد اولیه و بازیابی را ببینید. رد AI نباید سهمیه مصرف کند؛
   درخواست پذیرفته‌شده‌ای که بعداً خطای provider می‌گیرد طبق سیاست فعلی سهمیه مصرف می‌کند.
4. /pause، /cancel و /forget و تأیید حذف را هنگام فشار کم امتحان کنید؛ این مسیرها بودجهٔ مستقل
   دارند، نه مجوز عبور از تأیید/عضویت/مالکیت. پیام خود مالک همچنان takeover را اعمال کند.
5. یک broadcast کوچک با snapshot مخاطبان شناخته‌شده بسازید؛ هم‌زمان منو/پیش‌نویس را استفاده کنید؛
   محصول اولویت دارد و broadcast ممکن است عقب بیفتد. توقف، پیام تحویل‌شده را پس نمی‌گیرد.
6. در `/admin` ← «محافظت و ضداسپم» گزارش را ببینید و تازه کنید. خواندن گزارش خودش ترافیک UI
   دارد؛ اعداد قرار نیست ثابت بمانند. بررسی گزارش درخواست آزمایشی AI/تلگرام برای سلامت نمی‌سازد.
7. restart کنترل‌شده: فقط pending تأییدشدهٔ broadcast ادامه یابد، sending قدیمی unknown شود و
   cooldown ذخیره‌شده بازیابی شود. درخواست نامطمئن را برای «تست» کورکورانه دوباره نفرستید.
8. برای تولید429 واقعی سیل پیام به تلگرام نفرستید. مسیرهای flood/cancel/network با mock تست شده‌اند.

## معنی گزارش
- دسترسی فقط مدیر مجاز در خصوصی؛ کنترل سرویس report نیز مستقل است.
- شمارنده‌های تجمعی از شروع همین process و مجموع۱۵ سطل یک‌دقیقه‌ای جاری/اخیر (حدود۱۴تا۱۵دقیقه)
  نمایش داده می‌شوند. این sliding window دقیق ثانیه‌ای و گزارش روزانهٔ پایدار نیست.
- `AI accepted` پذیرش guard قبل از کنترل‌های بعدی است؛ ممکن است بعداً به‌دلیل عضویت/مکث/تکرار/
  quota هیچ AI اجرا نشود. برای مصرف واقعی از داشبورد مصرف استفاده کنید.
- اعلان مجاز یعنی guard اجازه داده؛ تضمین تحویل اعلان نیست. API success هم به معنی خوانده‌شدن پیام نیست.
- رد فوری خروجی، پرشدن انتظار و deadline به‌صورت شمارنده‌های جدا هستند؛ برای جمع ردها هر سه را لحاظ کنید.
- flood واقعی شامل429 از read/control هم می‌شود. success/failed/cancelled خروجی فقط متدهای paced
  را می‌شمارد. cancelled اینجا لغو بعد از پذیرش است؛ لغو هنگام انتظار شمارندهٔ ارسال ندارد.
- gaugeهای فعلی (فعال، منتظر، تعداد کلید، deadline) تصویر لحظه‌ای و best-effort هستند؛ نه high-water
  تاریخی، وضعیت کل سرور یا تعداد taskهای dispatcher. هیچ probe شبکه‌ای برای ساخت گزارش انجام نمی‌شود.
- متن/شناسه/لینک/کلید/بدنهٔ خطا و labels کاربرمحور در metrics نیست؛ فقط allowlist ثابت رویدادها.
  حداکثر۱۵ bucket و شمارنده‌های ثابت با اشباع عددی نگه داشته می‌شوند. DB/log per-message جدید نداریم.
- با restart آمار صفر می‌شود؛ deadline واقعیِ ذخیره‌شدهٔ flood مستقل است. نبود شمارندهٔ خطا اثبات
  نبود خطا در process قبلی، سالم‌بودن DB یا سالم‌بودن provider نیست. آمار محدودسازی اثبات حمله نیست.

## تنظیم تدریجی؛ بدون تغییر خودکار
ابتدا گروه کوچک دعوت کنید، روند گزارش را همراه مصرف روزانه/صورتحساب و لاگ امن بررسی کنید؛
بعد از پایدارشدن مسیرهای اصلی گروه را تدریجاً بزرگ کنید. آستانهٔ واحد و تضمینی برای همهٔ سرورها نداریم.
- **persistence_failed غیرصفر:** افزایش تعداد کاربر را متوقف کنید؛ DB/دسترسی جدول/اتصال را بررسی کنید.
  اگر DB خراب است، restart ممکن است مهلت ثبت‌نشده را از بین ببرد؛ به RAM فعلی و مهلت تلگرام احترام بگذارید.
- **flood واقعی:** نرخ ارسال را کم کنید (interval را بیشتر کنید)، broadcast را موقتاً متوقف کنید و
  deadline را رعایت کنید. retry فوری یا پاک‌کردن cooldown راه‌حل نیست.
- **global_busy/owner_busy زیاد:** ابتدا تأخیر AI/DB و کاربرد مشروع را بررسی کنید. زیادکردن concurrency
  بدون ظرفیت/بودجه ممکن است بحران را بدتر کند. عملیات تا پایان handler slot دارد، نه فقط زمان AI.
- **input/AI capacity زیاد:** هجوم شناسه یا ظرفیت نامتناسب ممکن است علت باشد؛ حافظه را کورکورانه
  بیشتر نکنید. TTL و ظرفیت محدود عمداً کلید تازه را fail-closed می‌کنند.
- **خطای خروجی/unknown:** با گزارش draft/broadcast تطبیق دهید؛ این metric علت دقیق یا تحویل قطعی
  را مشخص نمی‌کند. sends نامطمئن را خودکار بازپخش نکنید.
- **انتظار UI زیاد:** ابتدا بار broadcast و تأخیر خروجی را بررسی کنید؛ صف بزرگ‌تر الزاماً بهتر نیست.

هر بار فقط یک تنظیم تغییر دهید، مقدار قبلی را در یادداشت اپراتور نگه دارید، restart و چک‌لیست را
تکرار کنید. با مشکل هزینه، خطای کنترل مکث/مالکیت، ارسال تکراری یا نشت محتوا، دعوت عمومی را متوقف
و از مسیر مستقل توقف سرویس استفاده کنید؛ پنل بات تنها ابزار بازیابی نباشد. این مرحله auto-ban،
CAPTCHA، فیلتر محتوای AI، پایش OS/CPU/RAM یا محافظ توزیع‌شده اضافه نمی‌کند.

## اجرای تکرارپذیر آزمون آفلاین
در محیط توسعه با requirements نصب‌شده:
```sh
python -m pytest -q tests/test_protection.py tests/test_rate_limit.py tests/test_ai_guard.py tests/test_outbound.py tests/test_broadcast.py
python -m pytest -q
```
آزمون‌های فشار این فاز با ساعت/شبکهٔ ساختگی:
- ۱۰٬۰۰۰ کلید ورودی در یک burst: ظرفیت۱۶، پذیرش۱۶ و رد۹٬۹۸۴؛ مسیر ایمنی مستقل و بازیابی پس ازTTL.
- ۵٬۰۰۰ درخواست رقیب با۴ lease فعال AI: همه global_busy، فعال‌ها حداکثر۴؛ آزادسازی و پذیرش بعدی.
- ۱٬۰۰۰ درخواست خروجی در cooldown: حداکثر۸ منتظر،۹۹۲ رد ظرفیت انتظار، بدون network؛ لغو انتظارها
  و پذیرش دوباره پس از مهلت.
این اعداد تنظیمات fixture هستند، نه defaults production و نه ادعای تحمل۱۰هزارکاربر/ثانیه.
آزمون‌های موجود نیز cancellation، timeout، خطای شبکه/DB، restart/broadcast unknown، cooldown
پایدار و عدم مصرف quota در رد محافظ را پوشش می‌دهند. آزمون‌های آفلاین را علیه production اجرا نکنید.
