# مصرف امروز و عیب‌یابی پاسخ‌دهی

## منوی کاربر
دو ورودی خصوصی در داشبورد اضافه شده‌اند:
- «مصرف امروز»: سهمیهٔ واقعی User، رزروهای منطقی AI با تفکیک گفتگو/آزمایش، نتیجهٔ AI،
  پاسخ‌های واقعاً ارسال‌شده و ثبت‌شده، وضعیت فعلی draftهای ساخته‌شده امروز و موارد باز همهٔ روزها.
- «چرا پاسخ نمی‌دهد؟»: مکث کلی، حالت تأییدی/خودکار، ساعت محلی و timezone، سهمیه، وجود تنظیم کلید AI،
  بررسی زندهٔ اتصال‌های ثبت‌شده و can_reply. برای هر بخش، دکمهٔ اصلاح مربوط وجود دارد.
  بررسی گفتگوی منتخب، مکث محلی/تحویل مالک، علت تاریخی، سهمیه/ساعت فعلی و اتصال زندهٔ همان گفتگو را نشان می‌دهد.

تمام روزهای گزارش از 00:00 تا 24:00 UTC هستند، مطابق سهمیه؛ نه روز محلی ساعت کاری.
بازکردن/تازه‌کردن گزارش درخواست AI یا پیام به مخاطب نمی‌فرستد و سهمیه مصرف نمی‌کند.
آزمایش AI دکمهٔ جداگانه دارد که صریحاً مصرف سهمیه را اعلام می‌کند.

## قرارداد شمارش
- AiRequest یک **رزرو منطقی** است، نه تعداد درخواست‌های HTTP گوگل، توکن، قیمت یا صورتحساب.
  retry داخلی AI همان رزرو است. درخواست sandbox نیز سهمیه و گزارش دارد؛ ابزار CLI check_encoding
  که مستقیماً API را فراخوانی می‌کند جزو این گزارش نیست.
- کلید ثابت از مالک و شناسه‌های پیام/منبع هش می‌شود. پیام تکراری، رزرو یا مصرف سهمیهٔ جدید ندارد.
  sandbox هم به شناسهٔ پیام ورودی مقید است، نه UUID تازه برای هر retry.
- ردیف درخواست و افزایش سهمیه در یک تراکنش ایجاد می‌شوند. ردیف مالک در MySQL قبل از درج
  child دارای FK قفل می‌شود تا upgrade قفل مشترک FK به قفل نوشتن سهمیه موجب deadlock نشود.
- reserved: سهمیه رزرو شده اما نتیجه ثبت نشده؛ ممکن است هنوز در حال پردازش، قطع پروسه قبل/بعد از
  فراخوانی AI یا خطای نوشتن نتیجه باشد. این وضعیت اثبات ارسال درخواست یا شکست AI نیست.
- succeeded: خروجی معتبر AI تولید شده؛ به معنی رسیدن پیام به مخاطب نیست.
- failed: تولید خروجی ناموفق؛ سهمیه برنمی‌گردد. تنها کدهای allowlist مثل transport/http_429 ذخیره می‌شوند؛
  استثنای خام، بدنهٔ سرویس، URL، کلید و متن ورودی/خروجی ذخیره نمی‌شوند.
- denied: رزرو مجاز نشد و سهمیه‌ای مصرف نشد. کلیک/پیام تکراری همان درخواست ردیف جدید نمی‌سازد.
- نتیجهٔ نهایی AI یک‌طرفه ثبت می‌شود؛ به‌روزرسانی تکراری موفقیت را به شکست یا برعکس تبدیل نمی‌کند.
  شکست نوشتن نتیجه best-effort است و نباید AI یا send را تکرار کند؛ نوع خطا لاگ و reserved باقی می‌ماند.
- ارسال امروز از metadata direction=out/status=ok با زمان ثبت امروز شمرده می‌شود؛ پیش‌نویس دیروز
  که امروز ارسال و ثبت شده، جزو این عدد است. Telegram و DB تراکنش مشترک ندارند؛ اگر send موفق و
  ثبت DB ناموفق باشد، این عدد می‌تواند کمتر از ارسال واقعی باشد. عنوان «ارسال‌شده و ثبت‌شده» عمدی است.
- وضعیت draftها وضعیت **فعلی** رکوردهای ساخته‌شده امروز است، نه تعداد عملیات تاریخی. مثلاً draft
  منقضی که بعداً بسته شده در closed دیده می‌شود. expired حتی قبل از maintenance در گزارش محاسبه می‌شود.
- متادیتای inbound با یک کد علت نهایی/آخرین مرحله به‌روزرسانی می‌شود؛ جدول رویداد متن‌دار یا تاریخچهٔ کامل
  تمام علت‌های هم‌زمان نداریم. شمارش توقف‌ها تنها پیام‌های دارای متادیتای ورودی است؛ پیام مالک/بات دیگر
  یا پیام بی‌متن که در guardهای اولیه رد شده‌اند در این شمارش نیستند.

ثبت AI/علت‌های جدید از زمان نصب این نسخه آغاز می‌شود و backfill انجام نمی‌شود؛ سهمیهٔ User ممکن
است مصرف پیش از نصب در همان روز را هم داشته باشد. متادیتای ارسال/draft موجود قبلی در صورت موجودبودن
در گزارش خوانده می‌شود. ردیف‌های ai_requests متادیتا هستند و فعلاً تا حذف دادهٔ کاربر نگه داشته می‌شوند؛
پاک‌سازی متن draft و حافظهٔ کوتاه، سیاست‌های مستقل خود را دارند.

## معنی سلامت
بررسی API اتصال، اتصال‌های متعلق به همین مالک را refresh می‌کند؛ مالکیت پاسخ قبل از ذخیره بررسی می‌شود.
خطا یا مالکیت نامعتبر «نامشخص» است، نه اثبات قطع. نبودن connection در DB هم اثبات قطع در تلگرام نیست؛
از راهنمای یوزرنیم/قطع‌و‌وصل استفاده شود. Bot API فهرست کامل اتصال‌های گم‌شده را از طرف حساب ارائه نمی‌کند.
can_reply عمومی تضمین مجوز زمانی/ارسال در چت خاص یا اعتبار draft نیست. آخرین علت تاریخی نیز با
علت فعلی برابر نیست؛ تنظیمات جاری و نتیجهٔ زنده جدا نمایش داده می‌شوند.
وجود کلید تنظیم‌شده، اعتبار کلید، نام مدل یا دسترس‌پذیری AI را اثبات نمی‌کند. این بررسی به AI تماس نمی‌گیرد.
صفحه نیازمند DB عملیاتی است و مانیتورینگ بیرونی uptime یا بررسی اتصال DB خراب نیست.

## استقرار و rollback
migration جدید `0009_usage_health` جدول ai_requests و index مالک/زمان را با charset/collation صریح
ایجاد می‌کند. پس از بکاپ و توقف bot/watchdog، با پایتون محیط مجازی:
```bash
python -m alembic current
python -m alembic upgrade head
python -m alembic check
```
سپس restart/cron. head را stamp نکنید. downgrade این revision فقط متادیتای جدید درخواست AI را حذف
می‌کند، نه شمارندهٔ سهمیهٔ User و نه draftها. کد جدید بدون جدول جدید نباید اجرا شود.
/forget ردیف‌های ai_requests را پیش از حذف User پاک می‌کند؛ اطلاعات سرویس AI/Telegram مستقل است.

## تست دستی
1. گزارش را چندبار باز کنید: سهمیه و تعداد درخواست نباید زیاد شوند.
2. یک sandbox موفق و یک خطای AI در محیط تست ایجاد کنید؛ رزرو/نتیجه تغییر کند ولی ارسال به مخاطب صفر بماند.
3. draft بسازید و سپس تأیید کنید؛ تولید AI و ارسال، دو عدد مستقل باشند. کلیک تکراری نباید آمار جدید بسازد.
4. در حالت مکث/خارج از ساعت پیام تازه بفرستید؛ AI/سهمیه زیاد نشوند و علت توقف ثبت شود.
5. مجوز اتصال را تغییر دهید و عیب‌یابی را تازه کنید؛ snapshot قدیمی نباید به جای نتیجهٔ زنده نمایش داده شود.
6. قطع موقت API هنگام عیب‌یابی باید «نامشخص» بدهد، نه اعلام قطعی قطع.
7. حساب دوم هیچ آمار یا گفتگوی حساب اول را نبیند.
8. برای خطاها فقط عنوان امن دیده شود، نه کلید/بدنهٔ سرویس/متن گفتگو.

تست محلی شامل SQLite، migration roundtrip و SQL آفلاین MySQL و mock است؛ اجرای زندهٔ
MariaDB/Telegram و تست سناریو روی سرور همچنان لازم است. هیچ پرداخت یا پلنی در این فاز اضافه نشده است.
